# i18n / Translation Audit — Legal Suite (BEFORE state)

Audit date: 2026-08-31. Scope: `custom_addons/legal_core`, `legal_correspondence`,
`legal_procedure`, `legal_iq_registrar`, `legal_iq_tax`, `legal_iq_chamber`,
`legal_iq_social_security`, `legal_iq_residency`, `legal_iq_demo` against a running
`legal_dept` DB (port 8090) and the Odoo 19 source tree in `odoo-19.0/`.

## Summary

The suite ships **zero translation files** — no `i18n/` directory, no `.pot`, no `.po`
in any of the nine modules (neighbouring `dma_accreditation` and `gov_hr_*` modules in
the same repo do ship `i18n/ar.po`, so the precedent exists). Meanwhile **all five role
users (clerk, officer, approver, manager, auditor) run `ar_001`** and only `admin` runs
`en_US` (verified by SQL; both languages active in `res_lang`).

The source is **mixed-language, three ways at once**:

1. **The bulk is English** — 356 of 388 Python field labels, 99 of 138 selection labels,
   398 of 484 view-XML label attributes, all 74 OWL `_t()` strings, all ~30 sampled
   error messages, and every menu/action of `legal_core` and `legal_procedure`.
   With no `ar.po`, every one of these renders **in English on ar_001 screens**, while
   stock `base`/`web` *do* ship `ar.po` — so the Arabic user gets Arabic chrome
   (navbar, Save/Discard, filters) wrapped around an English application. This is the
   single largest defect versus the "Arabic-first, zero leakage" target: roughly the
   whole custom vocabulary leaks.
2. **A layer of baked bilingual strings** — 29 Python labels, 32 selection labels and
   17 XML attributes are single hard-coded strings of the form `"صادر - Outgoing"`.
   These are wrong in *both* languages, untranslatable, and stored in the DB under the
   `en_US` jsonb key.
3. **A layer of pure Arabic baked as the English source** — e.g. field label
   `م/ الموضوع`, menu `تسجيل كتاب وارد`, action `تدوين اتصال`, the entire 7-state
   document checklist vocabulary in `legal_constants.py`, and ~69 Arabic-only view
   attributes. These leak Arabic onto `en_US` screens and are invisible to the
   translation pipeline (they *are* the msgid).

DB ground truth confirms it: all 1,162 `ir_model_fields` rows for `legal.*` models,
every `ir_ui_menu.name`, `ir_act_window.name/help` and `ir_ui_view.arch_db` for the
suite hold **only an `en_US` key** — not a single `ar_001` value exists anywhere in the
database. `ar_001` rendering today is purely the `en_US` fallback.

The good news: the code discipline is largely translation-ready. 77 of 78 error raises
are wrapped in `_()`/`self.env._()`; the OWL layer has zero hard-coded Arabic outside
comments (74 `_t()` calls, English); the mail-room/desk labels are composed server-side
through `self.env._()` (102 call sites in `legal_dashboard.py`). The machinery to reach
the target is standard Odoo 19 gettext — what is missing is string normalisation plus
one complete `ar.po` per module.

## Detailed notes

### 1. How Odoo 19 actually resolves `ar_001` (verified in source)

- `odoo-19.0/odoo/addons/base/data/res.lang.csv:4` —
  `"base.lang_ar","Arabic / الْعَرَبيّة","ar_001","ar","Right-to-Left",...` — the locale
  code is `ar_001`, the ISO code is `ar`, direction RTL.
- `odoo-19.0/odoo/tools/translate.py:1780` `get_base_langs('ar_001')` → `['ar', 'ar_001']`.
- `odoo-19.0/odoo/tools/translate.py:1794` `get_po_paths(module, 'ar_001')` therefore
  probes, in order: `<module>/i18n/ar.po`, `<module>/i18n_extra/ar.po`,
  `<module>/i18n/ar_001.po`, `<module>/i18n_extra/ar_001.po`. **The file each module
  must ship is `i18n/ar.po`** (an `ar_001.po` would also load, after `ar.po`).
- Code translations are read *live from the po files at runtime*, not from the DB:
  `CodeTranslations` (`translate.py:1815`) keeps `{(module, lang): {src: value}}` maps.
  `_load_python_translations` filters po rows whose comment is `odoo-python`
  (`translate.py:54`) → feeds `_()` / `self.env._()`. `_load_web_translations` filters
  `odoo-javascript` (`translate.py:57`) → served to the webclient and applied by
  `@web/core/l10n/translation` `_t` and to OWL template terms. Consequence: with zero
  po files these maps are empty and every code string renders as its (English) msgid.
- Model terms (menu names, action names/help, view archs, translated data fields such
  as `name` on procedure types/steps/document types) live in **jsonb columns keyed by
  lang code**. Fallback: `odoo-19.0/odoo/orm/fields_textual.py:216`
  `get_translation_fallback_langs` returns `('ar_001', 'en_US')` — no `ar_001` key ⇒
  the `en_US` value is displayed verbatim. These jsonb values are only populated when a
  po file is imported (module install/update with the language loaded, or
  `odoo-bin i18n import`).
- Stock modules ship Arabic: `odoo-19.0/odoo/addons/base/i18n/ar.po` and
  `odoo-19.0/addons/web/i18n/ar.po` both exist — which is exactly why the shell of the
  app is Arabic for the role users while the legal suite content is not.

### 4. Reports

- `legal_correspondence/report/report_official_letter.xml` — 29 Arabic lines hard-coded
  in the QWeb body (`صفحة … من`, `مسودة - غير مقيدة في السجل`, `العدد:`, `التاريخ:`,
  `كتابكم المرقم:` …) with `dir="rtl"` and Arabic-Indic numeral localisation. An
  official Iraqi letter is an Arabic-only artifact, so a hard-Arabic body is a
  defensible *deliberate* exception — but it must be documented as such, and it is
  inconsistent with the stated target (English source + ar.po). Recommended: keep as
  exception OR convert the labels to terms and translate; do not leave implicit.
- `legal_correspondence/report/legal_correspondence_reports.xml:5,17` — report action
  names are mixed (`كتاب رسمي - ورق مطبوع / Official Letter (pre-printed paper)`) and
  leak into the Print dropdown; `:13,25` `print_report_name` = `'كتاب %s' % …`
  (download filename — acceptable Arabic, but decide once).
- `legal_core/report/` and `legal_procedure/report/` are **empty directories** — no
  report exists for cases, POAs or documents at all (separate functional gap).

### 5. The `legal_iq_*` data modules (~1,500+ Arabic lines)

`registrar_procedures.xml` (282 Arabic lines), `residency_procedures.xml` (166),
`tax_procedures.xml` (156), `tax_clearance.xml` (122), `registrar_bodies.xml` (113),
`psso_procedures.xml` (113), plus bodies/document-types/obligations/calendars per
module. These are *records* (procedure names, step names, body names, document types)
— domain content, mostly legitimately Arabic (`دائرة تسجيل الشركات` is a proper noun).
But they load into translatable jsonb fields **under the `en_US` key**, many as mixed
`"Arabic - English"` composites. So: ar_001 shows them via en_US-fallback (accidentally
correct), en_US shows Arabic, and no per-language variant exists. Data-file terms *are*
exported to the pot (`translate.py:1806` `get_datafile_translation_path` walks manifest
`data`+`demo` xml/csv), so the same po pipeline covers them once a source-language
policy is chosen (recommended: English-or-bilingual-free source values + `ar.po`
msgstr; proper nouns may stay Arabic in both).

`legal_iq_demo/data/demo_users.xml` sets the five role users to `ar_001` — consistent
with the Arabic-first target; keep.

### 6. Exact machinery to reach the target (English source + complete ar.po, zero leakage)

1. **Normalise sources (code change, per module):** split every mixed
   `"صادر - Outgoing"` string into English msgid; replace pure-Arabic labels
   (`م/ الموضوع` → `Subject`, checklist vocabulary in `legal_constants.py:56`, menu
   `تسجيل كتاب وارد`, wizard action names, 69 Arabic view attributes). Preserve the
   Arabic wording — it is the *correct msgstr* and moves into `ar.po` (e.g.
   `msgid "Outgoing"` / `msgstr "صادر"`). Decide and document the two deliberate
   exceptions: official-letter QWeb body, Arabic-Indic numeral helpers.
2. **Export the template** (Odoo 19 CLI, `odoo-19.0/odoo/cli/i18n.py:27`):
   `odoo-bin i18n export -d legal_dept legal_core legal_correspondence legal_procedure legal_iq_registrar legal_iq_tax legal_iq_chamber legal_iq_social_security legal_iq_residency`
   — default `-l pot` writes `i18n/<module>.pot` into each module (requires the
   modules updated in a DB first so model terms are current; run against a throwaway
   copy of the DB, not the live 8090 server).
3. **Author `i18n/ar.po` per module** (filename `ar.po`, not `ar_001.po`, per
   `get_base_langs`): translate every msgid; `Language: ar`. Model terms (menus,
   actions, selection labels, view archs, data record names) and code terms
   (`odoo-python`, `odoo-javascript` comment blocks) all live in the same file.
4. **Load:** ensure Arabic is loaded (`odoo-bin i18n loadlang -l ar` maps to
   `ar_001`/`base.lang_ar`), then update the modules with the language installed — the
   `TranslationImporter` fills the `ar_001` jsonb keys for model terms; code/web terms
   are served straight from the po at runtime (server restart clears the
   `CodeTranslations` cache). Verify by re-running the SQL from §2: every menu/action/
   field row must then show both `en_US` and `ar_001` keys.
5. **Guardrails (CI):**
   - a source scan failing on any `[؀-ۿ]` codepoint in `*.py`, `*.js`,
     `views/**/*.xml`, `wizard/**/*.xml` (allowlist: the two documented exceptions,
     data files pending the data-language decision);
   - po completeness: 0 untranslated / 0 fuzzy entries per `ar.po`
     (`msgfmt --statistics` or polib);
   - a smoke test logging in as `clerk@legal.iq` (ar_001) asserting no Latin script in
     menu labels / form labels on the key screens, and as `admin` (en_US) asserting no
     Arabic outside data values.
6. **RTL comes free:** `ar_001` is `Right-to-Left` in `res.lang.csv`; the web asset
   pipeline emits the RTL bundle automatically — no extra work beyond not hard-coding
   `dir`/`text-align` in backend SCSS (the report keeps its explicit `dir="rtl"`).
