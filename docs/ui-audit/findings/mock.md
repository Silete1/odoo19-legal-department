# Audit: AI Studio mock application ("Odoo 19 Entry Visas & Security Clearances")

Audited tree: `C:/Users/Lenovo/AppData/Local/Temp/claude/c--Users-Lenovo-Documents-odoo19/216c708f-55a1-4893-aecd-b4ff0e91075b/scratchpad/mock_app`
Stack: React 19 + Vite 6 + Tailwind v4 + lucide-react, generated by Google AI Studio (`metadata.json`, `README.md`).
Domain: entry visas & security clearances for Iraqi oil companies — a **sibling domain** to the legal-affairs target, used only as the visual starting point.

## Summary

The mock is a persuasive **single-page theatre piece**: five view modes (dashboard / list / kanban / form / pivot) switched by React state (`src/App.tsx:56,373-438`), all data in `localStorage` (`src/App.tsx:40-77`), all 5,200 lines hand-rolled to *look like* Odoo 19 (fake breadcrumbs, fake chatter, fake statusbar, a footer that literally says "Odoo 19 Enterprise · Online", `src/App.tsx:326-334`). Nothing in it is real Odoo, and its embedded "download the Odoo module" exporter produces below-standard Odoo code that must **not** seed the real modules.

What it is genuinely good at — and what earns porting into the legal suite — is **workflow storytelling for an Iraqi government paper trail**: a 13-state pipeline with consistent per-state colour tokens, KPI cards that drill into filtered lists, expiry countdown badges repeated in every view, صادر/وارد (outgoing/incoming) numbers surfaced on cards, an editable Arabic official-letter preview with letterhead/العدد/التاريخ/candidate-table/signatory/QR-verify, phase-coloured form sections, and Arabic-first RTL by default. These map cleanly onto native Odoo 19 primitives (statusbar, `widget="badge"`, list decorations, search filters, QWeb PDF, mail.activity, OWL desk tiles) — the mock validates the client's appetite; none of its *implementation* should survive.

What must be discarded: the Gemini/AI-Studio boilerplate (declared, never used), the module-code exporter, cosmetic client-side "roles" with zero enforcement, `Math.random()` document numbers, the dead Group-By selector, the fake pivot (three one-dimension breakdowns), and the click-anywhere status ribbon that jumps a record to any state without any permission check.

## Detailed notes

### 1. Architecture: a state machine impersonating a framework
`src/App.tsx` holds all state: requests array, role, language, viewMode, filter, four modal booleans (`:38-66`). Views are conditionally rendered components (`:373-438`); "navigation" cannot be bookmarked or shared. The whole app is wrapped in `select-none` (`:244`) — users cannot copy a passport number from the list. KPIs are recomputed inline on every render (`:97-116`), and notifications are rebuilt from scratch per render with `isRead: false` hard-coded (`:119-171`), including a literal Arabic string `'اليوم'` as a timestamp value (`:167`). None of this is portable; all of it is replaced by the ORM, actions and the webclient.

### 2. The workflow is the real spec
The 13-state selection (`types.ts:25-38`) with per-stage owner roles (`types.ts:8-14`), the stage-conditional actions (`VisaFormView.tsx:227-318`), and the chatter messages logged on each transition (`:84-107`) together encode the client's actual mental model of an Iraqi government paper flow: intake → internal approval → official letter with a registered number → ministry tracking by صادر/وارد → second-agency tracking → issuance with computed expiry → receipt → long-term follow-up. This is exactly the legal-affairs target's shape (request intake → approval → registered correspondence → court/agency tracking → deadline follow-up), which is why the *pipeline presentation* patterns transfer even though the domain does not.

### 3. The letter is the crown jewel — and the most dangerous to port naively
`printOfficialLetterHtml` (`exportUtils.ts:33-268`) is a decent visual spec: bilingual three-column letterhead, double-rule separator, العدد/التاريخ row, underlined subject, greeting, justified body, bordered candidate table, floated signatory block, faded diagonal watermark, footer with verification code and "printed by" line, `@page A4` margins. But: the state emblem is two emoji; the "QR" is a plain string; the signature is a bracketed placeholder; the subject/body/signatory are editable *at print time* (`OfficialLetterModal.tsx:134-193`) with no snapshot — an issued government letter must be immutable once numbered. Target: QWeb PDF, real assets, register-issued number, wizard-before-issue, stored rendering.

### 4. What the mock quietly gets wrong about "Odoo"
Beyond the exporter's code defects, the mock misrepresents several things stakeholders may now expect: a persistent dark sidebar (not an Odoo 19 pattern for a business app), "smart buttons" that navigate nowhere (`VisaFormView.tsx:366-384`), a chatter where "إشعار خاص" (log note) and comment differ only in button colour, and an "Enterprise" badge on what must be a Community deployment. The redesign should deliberately re-anchor expectations on native Odoo 19 idioms (per the user's standing expectation of substantial custom OWL work *inside* Odoo's architecture, not a lookalike shell).

### 5. Current legal suite baseline (for the comparison column)
Verified on `custom_addons/legal_*`: models cover cases, correspondence+registers+letter templates, procedures/phases/steps/transitions, obligations, POAs, SLAs, fees, documents/entities/gov-bodies (`grep _name` across `legal_*/models`). OWL dashboard screens exist (Mail Room, My Desk, body desk + kpi_tile/worklist/chart/phase_rail components). Gaps the mock throws into relief: **no pivot/graph view anywhere**, **no i18n/ar.po anywhere**, no suite-wide expiry-badge/decoration convention, and (per the target spec) no dedicated courts registry/hearings surface — "court" appears only in comments (`legal_procedure/models/legal_poa.py:72`).
